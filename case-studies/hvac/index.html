The engineering problem

Requirements are spread across prose, tables and pages. Multiple air-handling units can appear in the same document. Extracting a plausible value is insufficient: it must belong to the right equipment and point to supporting evidence.

What I implemented

01 · Prepare

Vision/OCR and table extraction build a document representation. LlamaIndex, hierarchical chunks and ChromaDB support retrieval.

02 · Extract

Identify equipment, map structured tables and combine deterministic rules with targeted language-model extraction.

03 · Check

Validate types and reconcile evidence. Cross-check source pages and equipment identifiers to flag values attributed to the wrong unit.

04 · Review

Export Excel and JSON with values, evidence and extraction method. Compare outputs against manually prepared references.

Why combine rules, retrieval and LLMs?

Tables provide explicit relationships that deterministic mapping can preserve. Retrieval narrows the context, while vision and language models handle less regular content. Validation remains a separate step because a fluent answer can still contain a wrong value or refer to another unit.

Download the input JSON and Python file into the same folder, then run python3 review-demo.py. The script recreates the output JSON and CSV using only the Python standard library. It demonstrates provenance checks; it does not run the private extraction pipeline.

What the evidence supports

The project includes manual-reference comparison, field-level provenance and tests for retrieval scope and equipment attribution. These are concrete engineering controls. Accuracy and processing time depend on the document, extraction path and evaluation set; no general performance claim is made here.

What still requires human review

Scans with poor legibility, ambiguous table headers, conflicting requirements and missing values. A source reference helps the reviewer verify a result; it is not proof that every extracted value is correct.
